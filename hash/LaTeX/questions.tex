A)
The problem is not very clearly described. At first, I thought I was given the
cycle $H^1(x), H^2(x), \dots, H^n(x)$ (without $x$ because otherwise just output

But after seeing question B), it seems that I should calculate the cycle itself,
and then use it to find a collision, with the condition that I store $\ll
\sqrt{2^{56}}$ bits. It is totally different then. If we should calculate such a
cycle from $x$, and stop immediately when we first have such a cycle, then there
are two cases:
\begin{enumerate}
	\item We have $H^n(x) = x$.
	\item We have $H^n(x) = H^m(x)$ for some $1 \le m < n$.
\end{enumerate}

There's a good algorithm, called Floyd's algorithm, to find the cycle while
storing only two (preimage, hash) pairs at all time. 
\begin{theorem}
Suppose starting from $x$, we first find a cycle at $H^n(x)$ for some $n$.
Define sequence $x_0 := x; x_{t+1} := H(x_t)$. Suppose there's a cycle that has
not subcycle, such that $x_m = x_n$ for $0 \le m < n$; and suppose that all
other elements in the sequence are distinct. Clearly, the sequence repeats after
$i \ge n$.

Then, for any $0 \le i$:
\begin{enumerate}
	\item If $i < m$, then $x_i \ne x_{2i}$.
	\item If $i \ge m$, then we have $x_i = x_{2i}$ iff $i \bmod (n-m) = 0$.
\end{enumerate}
\end{theorem}
\begin{proof}
If $i < m$, because the first few $m$ elements are distinct to all others, we by
definition have $x_i \ne x_{2i}$.

Now suppose $i \ge m$. By the cycle, we know that $x_{i} = x_{i \bmod (n-m)}$.
If $i \bmod (n-m) = 0$, then clearly $2i \bmod (n-m) = 0$, and $x_i = x_{2i}$;

if $x_{i} = x_{2i}$, then $x_{i \bmod (n-m)} = x{2i \bmod (n-m)}$. Thus, $i
\bmod (n-m) = (2 \bmod (n-m))(i \bmod (n-m))$. So we either have $2 \bmod (n-m)
= 1$ or $i \bmod (n-m) = 0$. But $2 \bmod (n-m)$ implies $n-m = 1$. Therefore,
we have $i \bmod (n-m) = 0$ anyway.
\end{proof}

The above theorem means that by the time $i = (n-m)$, we must have $x_{2i} =
x_i$. It also means it's the first time that this ever happens, thanks to the
iff. Thus, Floyd's algorithm is as follows:
\begin{quotation}
	Start from $i = 1$, check if $x_i = x_{2i}$. Stop at the first such $i$.
	Then, $i$ is the length of the smallest cycle, $n-m$, in the hash sequence. To
	actually find the cycle, apply $H^{n-m}$, start from $x_0$. If for some $j$,
	$H^{n-m}(x_j) = x_j$, then the first such $j = m$. And we are done.
\end{quotation}

Note that there's still an unfortuante possiblility that $m = 0$, in which case
the cycle does not result in a collision. It is unfortunate, and for that I
thought a lot, see the discussion in \textbf{One possible scenario} and
\textbf{Another possible scenario}. 

The following two discussions actually happen before I realize Floyd's
algorithm. One reason is that I incorrectly estimated the number $\sqrt{2^{56}}
\approx 3 \times 10^8$ to be too large to finish in 15 minutes.  Thus, I thought
the cycle is needed to also \emph{speed up} the calculation. The following text
is a result of that misconception: \textbf{I was contemplating how having a
cycle may also speed up the collision-discovery.}

\paragraph{One possible scenario}
Let $x$ be any input. I am given $H_0 := H(x), H_n := H(H_{n-1})$, and I know
that for some $m$, $H_m = H_0$ (assuming no subcycles, i.e., $m$ is the smallest
number to have a cycle from $H_0$).

However, I am not given $x$; I only have the values $(H_n)_{n=0}^m$.  Because I
don't know $x$, I can't use the collision $H(x) = H(H_{m-1})$; I don't even know
if $x = H_{m-1}$ or not.

Note that I have both $H_0 = H_m$ by cycle and $H^{m}(H_0) = H_m$ by induction
on the definition of $(H_n)_{n=0}^m$. It then turns out $H_0 = H^m(H_0)$. Thus,
for all natural number $i$, $H^{im}(H_0) = H_0$. Moreover, because it is a
cycle, we can be more general:
\begin{equation} \label{eq:q4a.1}
	\forall i\ j \in \mathbf{N},\ 
	H^i (H_j) = H^{i \bmod m} (H_{j \bmod m}) = H_{(i+j) \bmod m}
\end{equation}
There's also a little more piece of information; since $m$ is the smallest
number for which we have a cycle, 
\begin{equation} \label{eq:q4a.2}
	\forall i \ne j \mod m,\ 
	H_i \ne H_j
\end{equation}

Note how similar the structure is to Fermat's little theorem. This discovery is
amazing, but I don't immediately see how \eqref{q4a.1} helps me find a
collision faster. On the other hand, the more trivial \eqref{q4a.2} helps me,
only a little. It essentially provides $m$ distinct pairs of preimages and
hash values, i.e., $(H_i, H_{i+1})_{i=0}^{m-1}$. So I benefit from here doing
$m$ less calculations.

But I fail to see how to use \eqref{q4a.1} to help. I asked a question here 
\url{https://crypto.stackexchange.com/questions/115058/how-can-having-a-cycle-help-finding-a-hash-collision},
which may find an answer later.

\paragraph{Another possible scenario}
I later read Section 6.4.3 of [Katz, Lindell, 3rd ed.], which assumes that the
length of the cycle equals exactly the cardinality of the range of $H$, which
isn't explicitly mentioned in the question.

Well, anyway, so this possible scenario is essentially the previous one plus
this additional information:
\begin{equation}
	m = \text{ size of the range of } H
\end{equation}

How does this seemingly unimportant information help? Well, it actually
guarantees that every hash values falls into the cycle, which is very important.
Under this strong guaranteen, we don't have to store all experienced (preimage,
hash) pair to succeed.

[Katz, Lindell] gives this even division scheme: partition the whole range,
i.e., the cycle, into $\sqrt{m}$ segments, each of length $\sqrt{m}$. Here's the
clever part: one only stores the start and end of each segment, i.e.,
$(H_{i\sqrt{m}},, H_{(i+1)\sqrt{m}})$. Thus, we only have to store $2\sqrt{m}$
pairs in worst case (actually, now, in all cases), whereas previously we needed
to store $m$ pairs.

The algorithm runs as follows: given any hash value $y$, we can find a preimage
of it inside the range of $H$, because the cycle covers the whole range, $y$
must fall into one of the segments. 
\begin{enumerate}
\item If $y$ is one of the end points $H_{(i+1)\sqrt{m}}$, then doing
	$\sqrt{m}-1$ hashes from the start point gives a preimage of $y$.
\item If otherwise $y$ is inside a segment, then applying $H$ less than
	$\sqrt{m}$ times is guaranteed to reach a endpoint. Then, we find its
	startpoint, and start to do $\sqrt{m} - 1 - $ the number of $H$ on $y$ to
	reach the endpoint hashes.
\end{enumerate}

This gives an algorithm to find a preimage inside the range, for any hash value.
Thus, to turn it into a collision, one simply picks any value out of the range,
calculate its hash, and use the algorithm to find another preimage that's inside
the range.

To store even less bits, reduce the number of segments, which will in turn
increase the number of hashes we need to do. It is possible to store less than
$\sqrt{m}$ bits while being able to still do it faster than brute force.
